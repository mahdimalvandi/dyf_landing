# سند استاندارد فرآیند و چرخه انجام تسک‌ها (Task Execution Flow)
**پروژه:** DYF Private Catalog Backend  
**مخاطبان:** توسعه‌دهندگان، معماران و ایجنت‌های هوش مصنوعی (AI Agents)

---

## مقدمه و هدف
این سند مشخص‌کننده فرآیند رسمی، الزامی و مرحله‌به‌مرحله انجام کلیه تسک‌های پروژه است. هیچ تسکی بدون طی کردن تک‌تک مراحل این چرخه آغاز یا وارد کدبیس اصلی نخواهد شد.

---

## چرخه ۷ مرحله‌ای انجام تسک (The 7-Step Task Lifecycle)

```text
[۱. تدوین سند تحلیل] ──> [۲. بازبینی و تایید کاربر] ──> [۳. ساخت برنچ جدید] ──> [۴. رفع ابهامات و سوالات]
                                                                                     │
[۷. مرج نهایی] <── [۶. ریویو کد توسط کاربر و فیکس] <── [۵. پیاده‌سازی مینیمال و تست] <──────┘
```

---

### مرحله ۱: تدوین سند جامع تحلیل فنی (Technical Analysis)
قبل از نوشتن حتی یک خط کد، باید یک سند تحلیل فنی دقیق و شفاف ایجاد شود.
- **محل ذخیره سند:** `docs/backend/analysis/task_XX_<task_name>.md`
- **محتوای اجباری سند تحلیل:**
  1. **تحلیل پایگاه داده:** 
     - نیاز یا عدم نیاز به جدول دیتابیس جدید یا تغییر جداول موجود.
     - نام جداول و ستون‌ها به صورت دقیق با فرمت camelCase و دابل‌کوتیشن.
     - نوع فیلدها (BIGINT برای زمان و شناسه، JSONB، VARCHAR و...).
     - ایندکس‌های موردنیاز (B-Tree یا GIN).
  2. **طراحی Endpointها و مشخصات دقیق APIها:**
     - متد HTTP و آدرس روت (Route Path).
     - استراکت ورودی (Request Body / Query Params / URL Params).
     - استراکت خروجی (Response DTO).
     - رسیورها و توابع اعتبارسنجی ورودی.
  3. **معماری جریان داده و لایه‌ها:**
     - وظایف لایه Controller / Handler.
     - وظایف لایه Service و بیزینس لاجیک.
     - وظایف لایه Repository و کوئری‌ها.
  4. **سیستم مدیریت خطاها:**
     - کلیدهای خطای جدید در `statics/errors/customErrors.go`.
     - معادل متن فارسی خطاها در `statics/errors/faTranslation.go`.
     - وضعیت‌های HTTP متناظر برای هر خطا.
  5. **سناریوهای تست و لبه‌ها (Edge Cases):**
     - سناریوهای موفق (Happy Paths).
     - سناریوهای شکست، ولیدیشن و خطاهای دسترسی.
- **وضعیت در پایان مرحله:** متوقف شدن و تحویل سند به کاربر برای بررسی.

---

### مرحله ۲: بررسی، بازبینی و اصلاح تحلیل توسط کاربر (Review & Approval)
- کاربر سند تحلیل را با دقت مطالعه کرده و اصلاحات، تغییرات یا نیازهای تکمیلی را اعلام می‌کند.
- ایجنت سند را بازبینی و طبق نظر کاربر به‌روزرسانی می‌کند.
- **شرط عبور به مرحله بعد:** اعلام رضایت قطعی و دستور مستقیم کاربر مبنی بر «تأیید شد / انجام بشه».

---

### مرحله ۳: ساخت برنچ اختصاصی تسک (Branch Creation)
- ایجاد و سوییچ به یک برنچ Git مستقل با نام معنادار و متناسب با تسک.
- الگو: `feat/task-XX-<task-name>` (مثال: `feat/task-01-admin-login`).

---

### مرحله ۴: استعلام ابهامات و پرسش قبل از کدنویسی (Clarifications)
- هرگونه نکته مبهم، شک در الگوی پیاده‌سازی یا کمبود اطلاعات باید فوراً از کاربر پرسیده شود.
- اصل **Zero Guessing & Zero Dead-Code Policy** به صورت سخت‌گیرانه رعایت می‌شود.
- تا زمان تکمیل و شفافیت ۱۰۰٪ اطلاعات، فرضیه‌سازی شخصی ممنوع است.

---

### مرحله ۵: پیاده‌سازی با کمترین حجم کد و تست سناریوها (Implementation & Testing)
- **اصل کمترین حجم کد و بالاترین خوانایی (Minimal Code Volume & High Readability):** ساده‌ترین و تمیزترین رویکرد پیاده‌سازی انتخاب می‌شود.
- رعایت استانداردهای اصلی:
  - ساختار تفکیک‌شده خانواده‌های API (`internal/dto/`, `internal/entity/`, `internal/handler/`, `internal/service/`, `internal/repository/`).
  - **ممنوعیت کامل کامنت (Zero Comments)**.
  - **ممنوعیت متغیرهای تک‌حرفی**.
  - شناسه `"ID"` از نوع `int64` نانوثانیه و عدم استفاده از `createdAt`.
- **تست جامع سناریوها:**
  - تست سناریوهای مختلف کارکرد درست و اعتبارسنجی خطاها.
  - در صورت نیاز به دیتابیس واقعی، اطلاعات اتصال از کاربر دریافت شده و مایگریشن و کوئری‌ها روی دیتابیس واقعی تست می‌شوند.

---

### مرحله ۶: بازبینی کد توسط کاربر و رفع مشکلات (User Code Review & Fixes)
- ارائه گزارش شفاف از کدهای پیاده‌سازی‌شده و سناریوهای تست‌شده به کاربر.
- بررسی دقیق کدها توسط کاربر.
- اگر ایراد یا باگی مطرح شد، ایجنت فوراً آن را فیکس و اصلاح می‌کند.

---

### مرحله ۷: ادغام نهایی (Merge)
- تنها پس از تأیید نهایی و اعلام صریح کاربر مبنی بر «مرج بشه»، برنچ تسک با برنچ اصلی ادغام (Merge) می‌شود.
