# راهنمای جامع ایجنت‌های هوش مصنوعی (AI AGENT PLAYBOOK)
**پروژه:** DYF Private Catalog Backend  
**مخاطب:** هر دستیار هوش مصنوعی و مدل زبانی (LLM) که در این پروژه وظیفه توسعه کد، بازبینی، معماری یا عیب‌یابی دارد.

---

## ۱. اصل بنیادین و طلایی رفتار Agent (بسیار حیاتی)

**قانون منع حدس و گمان و پیشگیری از تولید کد مرده (Zero Dead-Code Policy):**

1. هر زمان، در هر تسک و در هر مرحله از کار:
   - اطلاعاتی را به صورت شفاف و قطعی نمی‌دانستید،
   - نمی‌دانستید کدام روش و تکنیک بهتر یا موردنظر است،
   - شک داشتید که آیا پروژه از یک پکیج، ابزار یا الگوی خاص استفاده می‌کند یا خیر،
   - زمینه و کانتکست کافی برای تصمیم‌گیری نداشتید،
   **به هیچ عنوان، تحت هیچ شرایطی، به صورت حدسی جلو نروید.**
2. حدس زدن منجر به ایجاد فرضیات نادرست و **تولید کدهای زائد و مرده (Dead Code)** می‌شود. بنابراین هر جا نیاز به تصمیم‌گیری یا روشن شدن موضوعی بود، **فوراً و مستقیماً از کاربر بپرسید.**
3. **اصل کمترین حجم کد و بیشترین خوانایی (Minimal Code Volume & High Readability):**
   - هر مسئله، باگ یا تسکی را با **کمترین تعداد خطوط کد ممکن** و به **خواناترین و تمیزترین روش ممکن** پیاده‌سازی کنید.
   - چنانچه برای حل یک مسئله چند رویکرد فنی وجود داشته باشد، علاوه بر عملکرد (Performance)، **حجم کم کد** و **خوانایی بالا** اولویت قطعی انتخاب هستند.

## ۲. چرخه استاندارد و پروتکل مرحله‌به‌مرحله اجرای هر تسک (Task Execution Flow)

هر تسکی که برای پیاده‌سازی اعلام می‌شود، **باید دقیقاً طبق این ۷ گام** پیش برود و هیچ گامی نباید دور زده شود:

1. **گام ۱ - تدوین سند تحلیل فنی (Technical Analysis & RFC):**
   - پیش از نوشتن هر کدی، یک سند تحلیل فنی کامل در مسیر `docs/backend/analysis/task_XX_<name>.md` ایجاد می‌شود.
   - سند باید شامل: ساختار دقیق جداول دیتابیس (فیلدها، نوع‌ها، ایندکس‌ها)، تعریف دقیق APIها (متد، مسیر، DTOهای Request و Response)، لایه‌بندی سرویس/ریپازیتوری/کنترلر، مدیریت خطاها و معادل فارسی، و سناریوهای تست باشد.
   - **توقف الزامی:** کار متوقف شده و سند به کاربر جهت بررسی و فیدبک ارائه می‌شود.

2. **گام ۲ - بازبینی، اصلاح و تأیید نهایی توسط کاربر:**
   - کاربر تحلیل را بررسی کرده و تغییرات را اعلام می‌کند.
   - ایجنت سند تحلیل را طبق نظر کاربر اصلاح می‌کند.
   - تا زمانی که کاربر صراحتاً نگوید «تأیید شد / انجام بشه»، کدنویسی آغاز نخواهد شد.

3. **گام ۳ - ساخت برنچ جدید برای تسک:**
   - ساخت یک برنچ Git مستقل با نام تسک (مانند `feat/task-01-admin-login`).

4. **گام ۴ - رفع ابهامات و پرسش‌های تکمیلی (Clarifications):**
   - هر نکته مبهم، سوال فنی یا نیاز به جزئیات بیشتر، بلافاصله از کاربر پرسیده می‌شود (منع حدس و گمان).

5. **گام ۵ - پیاده‌سازی مینیمال و تست سناریوها:**
   - پیاده‌سازی با حداقل تعداد خطوط کد و حداکثر خوانایی طبق استانداردهای کدنویسی (بدون کامنت، camelCase، ساختار API Family).
   - تست تمام سناریوهای موفق، ناموفق و حالت‌های لبه (در صورت نیاز به دیتابیس، اطلاعات کانکشن از کاربر گرفته می‌شود).

6. **گام ۶ - ریویو توسط کاربر و رفع مشکلات (Fixes):**
   - ارائه گزارش کامل پیاده‌سازی و تست‌ها به کاربر.
   - بررسی کد توسط کاربر و رفع سریع هرگونه باگ یا نکته اعلام‌شده.

7. **گام ۷ - مرج نهایی:**
   - ادغام برنچ با برنچ اصلی صرفاً پس از دستور مستقیم کاربر («مرج بشه»).

## ۳. قوانین ساختاری و معماری پروژه‌محور (Strict Architectural Rules)

### ۳.۱. تفکیک پوشه‌ها بر اساس خانواده‌های API (API Family Architecture)
در تک‌تک لایه‌های زیر به ازای هر موجودیت/جدول دیتابیس (مانند `customer`, `shoes`, `category`, `accessLink`, `auth`, `catalog`) یک پوشه مجزا وجود دارد:
- **`internal/dto/<family>/`:**
  - `request.go` (استراکت‌های ورودی)
  - `response.go` (استراکت‌های خروجی)
  - `recievers.go` (متدها و رسیورهای مربوط به Request و Response)
- **`internal/entity/<family>/`:**
  - `entity.go` (تنها تگ مجاز GORM تگ `column` است).
- **`internal/handler/<family>/`:**
  - **یک استراکت واحد به نام `Handler` در `handler.go`** همراه با سازنده `NewHandler(service service.Service) Handler`.
  - هر API به صورت یک **متد (Receiver)** روی همان استراکت `Handler` در فایلی به نام همان API نوشته می‌شود (`sendOTP.go`, `verifyOTP.go`, ...).
  - استفاده سراسری از `request.ParseBody(fiberContext, &req)` برای بایندینگ، نرمال‌سازی و هندل خودکار خطاهای ولیدیشن.
- **`internal/service/<family>/`:**
  - **یک استراکت واحد به نام `Service` در `service.go`** همراه با سازنده `NewService(...) Service`.
  - هر API یک متد روی استراکت `Service` است و علاوه بر دیتا و ارور، کد وضعیت HTTP (`statusCode int`) را بازمی‌گرداند (`(res, statusCode, err)`). بدین ترتیب لایه هندلر نیازی به `if/else`های طولانی ندارد.
  - لایه سرویس هیچ وابستگی به فریمورک Fiber ندارد.
- **`internal/repository/<family>/`:**
  - یک استراکت واحد به نام `Repository` در `repository.go` که تمام کوئری‌ها متدهای آن هستند.
- **`statics/constants/<family>/`:**
  - `constants.go` (ثابت‌های اختصاصی همان خانواده).

### ۳.۲. سیستم خطاها و ترجمه فارسی (`statics/errors/`)
1. **هیچ Status Code در تعریف خطاها قرار نمی‌گیرد.**
2. در `statics/errors/customErrors.go`:
   - یک ثابت رشته‌ای برای هر خطا: `const UserNotFound = "userNotFound"`
   - یک ارور استاندارد Go: `var ErrUserNotFound = errors.New(UserNotFound)`
3. در `statics/errors/faTranslation.go`:
   - مپ `PersianErrorRegistry` با کلید نام خطا و مقدار ترجمه فارسی: `UserNotFound: "کاربر مورد نظر یافت نشد"`.
4. لایه سرویس علاوه بر ارور، کد وضعیت HTTP متناظر را هم برمی‌گرداند؛ لایه هندلر بدون if/else اضافی پیام فارسی را با `response.FromError(fiberContext, statusCode, err, details)` برمی‌گرداند.

### ۳.۳. ساختار راه‌اندازی و ثبت ماژولار روت‌ها (`cmd/server/`)
- **`cmd/server/main.go`:** لود کانفیگ و راه‌اندازی سرور.
- **`cmd/server/routes/<family>.go`:** به ازای هر خانواده API یک فایل ثبت مسیر حاوی تابع `Register<Family>Routes(apiGroup, db)` که اینیشیالایز ریپازیتوری، سرویس و هندلر در آن انجام می‌شود.
- **`cmd/server/route.go`:** صرفاً توابع ماژولار پکیج `routes` را صدا می‌زند.
- **دسترسی سراسری به کانفیگ (`config.Get()`):** نیازی به ارسال زنجیره‌ای `appConfig` در ورودی سازنده‌ها نیست؛ هر پکیج مستقیماً `config.Get()` را می‌خواند.

### ۳.۴. پایگاه داده و مایگریشن با `golang-migrate`
- **قانون قطعی: به ازای هر جدول دیتابیس دقیقاً یک فایل مایگریشن.** هیچ‌وقت چند جدول در یک فایل قرار داده نمی‌شوند.
- جدول `"schemaMigrations"` به صورت خودکار توسط کتابخانه ساخته و رهگیری می‌شود و نیازی به مایگریشن دستی ندارد.
- تمام خطاها و موفقیت‌ها به صورت شفاف با `[MIGRATE ERROR]` و `[MIGRATE SUCCESS]` در کنسول لاگ می‌شوند.

## ۴. قوانین نگارش کد Go (Coding Rules)

1. **ممنوعیت کامل کامنت در کدها (Zero Comments):** هیچ کدی نباید هیچ‌گونه کامنتی (`//` یا `/* */`) داشته باشد.
2. **قانون نام‌گذاری شتری (camelCase) و ممنوعیت متغیرهای تک‌حرفی:** تمام متغیرها، پارامترها و پکیج‌های مستعار ایمپورت (Import Aliases) باید با ساختار توصیفی camelCase نام‌گذاری شوند (مانند `constantsAuth`, `dtoAuth`, `entityAuth`, `repoAuth`, `serviceAuth`, `handlerAuth`, `staticErrors`, `jsonIter`؛ استفاده از شکل سرهم و کوچک مثل `constantsauth` اکیداً ممنوع است). تنها استثنای تک‌حرفی: شمارنده ایندکس حلقه `i` یا `index`.
3. **شناسه `"ID"` نانوثانیه و حذف `createdAt` و `updatedAt`:** فیلد `"ID"` از نوع `int64` معادل `time.Now().UnixNano()` است و فیلدهای `createdAt` و `updatedAt` وجود ندارند (مگر درخواست صریح کاربر). همچنین برای جداول کم‌حجم یا موقت هیچ ایندکس اضافه‌ای ساخته نمی‌شود.
4. **سیاست مقداری (Value-Type):** تا جای ممکن از ساختارهای مقداری استفاده کنید و از تعریف پوینترهای غیرضروری پرهیز کنید تا ریسک خطای `nil pointer` از بین برود.
5. **قرارداد ۳ خروجی در Getهای ریپازیتوری:** `(item, found, error)` که در صورت نیافتن رکورد `found = false` و `error = nil` است.
6. **احراز هویت توکن‌محور و هش MD5 (حذف کامل JWT):** احراز هویت با توکن‌های مات تصادفی است؛ هش MD5 توکن در جدول دیتابیس ذخیره و کوئری می‌شود.
7. **پیکربندی کامل از طریق `.env` و متد `config.Get()`:** تمام اتصالات و مشخصات بدون هاردکد شدن از طریق `config.Get()` در دسترس کل سیستم هستند.
8. **پاکسازی فایل‌های تست:** فایل‌های تست آزمایشی نباید پس از پایان تست در مخزن پروژه رها شوند.

## ۵. دستورات پرکاربرد محیط توسعه

```bash
# رفتن به پوشه بک‌اند
cd backend

# تست بیلد و کامپایل بدون خطا
go build ./...

# اجرای وب‌سرور
go run cmd/server/main.go

# دستورات مایگریشن دیتابیس
go run cmd/migrate/main.go up
go run cmd/migrate/main.go down
go run cmd/migrate/main.go version
```
