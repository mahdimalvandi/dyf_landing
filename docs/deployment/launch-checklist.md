# آمادگی انتشار DYF

## تغییرات فنی این برنچ

- دامنهٔ canonical، اشتراک‌گذاری و sitemap: `https://dyfshoes.ir`.
- تصویر ثابت نشان به‌صورت پیش‌فرض نمایش داده می‌شود. مدل سه‌بعدی فقط پس از تشخیص WebGL بارگذاری می‌شود و فقط بعد از آماده‌شدن جای تصویر را می‌گیرد. در حین بارگذاری طولانی یا خطا، تصویر باقی می‌ماند.
- در موبایل نشان سه‌بعدی قبل از معرفی و دکمه‌ها قرار دارد؛ اگر مدل بارگذاری نشود، تصویر دوبعدی لوگو جای آن نمایش داده می‌شود. منو وضعیت ARIA، کنترل Tab، Escape و بازگرداندن فوکوس دارد.
- ورودی‌های پنل و کاتالوگ `noindex` و `no-referrer` دارند. هدرهای API و رسانه نیز از ایندکس و کش خصوصی جلوگیری می‌کنند.
- درخواست‌های OTP و فرم عمومی محدود شده‌اند؛ قرارداد handler-first در Fiber v3 رعایت شده و تست دارد. ترتیب middlewareهای قبلی مشکل نداشت؛ ارسال OTP مدیر هم اکنون محدودکننده دارد.
- production با OTP آزمایشی، تنظیمات ناقص پیامک یا کلید رسانهٔ ضعیف اجرا نمی‌شود.
- فایل‌های `/uploads` دیگر عمومی نیستند: لینک دارای امضای HMAC و اعتبار محدود است. رسانهٔ کاتالوگ علاوه بر امضا، وضعیت فعال‌بودن و انقضای مجوز و مشتری را نیز بررسی می‌کند. فایل‌های ثابت عمومی برند عمداً عمومی می‌مانند.

## تنظیمات سرور

1. `npm ci` و `npm run build` در `frontend`؛ `go test ./...` و build در `backend`.
2. در backend: `APP_ENV=production`، `OTP_PROVIDER=msgway`، کلید و قالب واقعی MsgWay، مشخصات واقعی پایگاه داده.
3. تولید یک `MEDIA_SIGNING_KEY` تصادفی و پایدار، حداقل ۳۲ بایت؛ مثلاً با `openssl rand -hex 32`. در مخزن commit نشود. تغییر کلید تمام آدرس‌های رسانهٔ قبلی را نامعتبر می‌کند؛ ورود مجدد به کاتالوگ آدرس تازه می‌دهد.
   در محیط توسعه، خالی‌بودن این مقدار کلید موقت تصادفی ایجاد می‌کند؛ با راه‌اندازی مجدد backend آدرس‌های قبلی نامعتبر می‌شوند. تمام نمونه‌های production باید کلید پایدار یکسان داشته باشند.
4. `CORS_ALLOWED_ORIGINS=https://dyfshoes.ir`؛ اگر frontend و API هم‌دامنه نیستند، `VITE_API_BASE_URL` را پیش از build تنظیم کنید. مقدار originها باید دقیق و بدون اسلش پایانی باشد.
5. از `nginx.conf.example` با مسیر نصب و گواهی واقعی استفاده کنید. backend فقط از شبکهٔ داخلی/loopback در دسترس باشد. مسیر `/uploads` حتماً به backend پروکسی شود، نه فایل‌سرور یا CDN عمومی.
6. محدودکنندهٔ فعلی بر IP اتصال backend تکیه دارد. پشت یک reverse proxy، بدون تنظیم و آزمون IP پراکسیِ مورداعتماد، کاربران ممکن است یک سهمیهٔ مشترک داشته باشند. از اعتماد عمومی به `X-Forwarded-For` خودداری کنید؛ در استقرار نهایی trusted proxy یا محدودسازی لبه را متناسب با زیرساخت تنظیم و تست کنید.
7. در production هرگز Vite dev server را منتشر نکنید. DNS، TLS، ریدایرکت www و HTTP، تمام مسیرهای `/catalog`، `/catalog/<token>`، `/admin` و بارگذاری فایل را آزمایش کنید.
8. از PostgreSQL و پوشهٔ uploads نسخهٔ پشتیبان خارج از سرور بگیرید و بازیابی هر دو را آزمایش کنید. این برنچ زیرساخت پشتیبان‌گیری را مستقر نمی‌کند.

## محدودیت‌های عمدی حفاظت رسانه

- امضای رسانهٔ پنل یک ساعت اعتبار دارد؛ بعد از آن داده‌ها را تازه‌سازی کنید. رسانهٔ کاتالوگ حداکثر یک ساعت و نه بیشتر از عمر مجوز اعتبار دارد؛ بررسی دوره‌ای نشست کاتالوگ لینک‌ها را تازه می‌کند.
- لینک امضاشده تا زمان انقضا یک اعتبار دسترسی قابل انتقال است؛ توکن اصلی کاتالوگ در آن قرار نمی‌گیرد. ابطال مجوز کاتالوگ جلوی درخواست‌های بعدی فایل را می‌گیرد، نه فایل دانلودشده یا اسکرین‌شات را.
- فقط رسانهٔ بارگذاری‌شدهٔ محلی محافظت می‌شود؛ URL خارجی تابع سیاست سرور میزبان خودش است.
- این اصلاحات جای ممیزی کامل امنیت، آزمون فشار یا اعتبارسنجی قرارداد پیامک واقعی را نمی‌گیرد.

## نیازمند اطلاعات و تأیید مالک برند

- صحت شماره‌ها، آدرس، حساب‌های رسمی و مالکیت دامنه؛
- سابقه، محل تولید، متریال، حداقل سفارش و خدمات واقعی؛
- جایگزینی تصاویر آزمایشی با عکس‌های مجاز واقعی؛
- تأیید عبارت انگلیسی برند و تمام ادعاهای فنی/سلامتی؛
- تعیین مسئول و زمان پاسخ‌گویی به درخواست همکاری.

محتوای تجاری و تصاویر فعلی بدون تأیید تغییر نکرده‌اند. تا تکمیل این فهرست، چاپ کارت و معرفی عمومی به‌عنوان نسخهٔ نهایی توصیه نمی‌شود.
